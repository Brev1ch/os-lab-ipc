## Часть 1. Сигналы

### Теория (кратко)

- Сигнал: асинхронное уведомление процесса о событии (от ядра, терминала или другого процесса через `kill`).
- Реакция (диспозиция): действие по умолчанию, игнорирование (`SIG_IGN`) или собственный обработчик. `SIGKILL` и `SIGSTOP` нельзя ни перехватить, ни игнорировать, ни заблокировать.
- Ненадёжные сигналы (`signal`): после доставки диспозиция сбрасывается в `SIG_DFL` (нужно переустанавливать обработчик), сигнал нельзя заблокировать на время критического участка. Между запуском и переустановкой обработчика есть окно, в котором второй сигнал убьёт процесс.
- Надёжные сигналы (POSIX, `sigaction`): обработчик установлен постоянно, есть маска сигналов (`sa_mask`), на время обработчика сам сигнал и сигналы из маски блокируются, доставка откладывается до выхода из обработчика. Обычные сигналы не ставятся в очередь: несколько одинаковых ожидающих сигналов сольются в один.

### Уровень 3 (A): `threads_sig.c`

Свой пример с двумя нитями (исходной программы из лекции 2 в материалах нет). Нить 1 через 3 с шлёт нити 2 `SIGUSR1` через `pthread_kill(t2, SIGUSR1)`. Сборка: `gcc -pthread -DVARIANT=N`. (Вместо `/lib/libthread.so.0` из методички в современных системах используется флаг `-pthread`.)

| VARIANT | Что происходит | Результат |
|---|---|---|
| 1 | обработчика нет, действие по умолчанию | погибает **весь процесс** (код 138 = SIGUSR1), а не только нить |
| 2 | свой обработчик только печатает сообщение | нить 2 печатает «пришёл SIGUSR1» и продолжает работать |
| 3 | обработчик печатает и вызывает `pthread_exit(NULL)` | гибнет только нить 2, процесс завершается штатно |

Вывод варианта 3:

```
thread2: работаю, тик 3
thread1: pthread_kill(t2, SIGUSR1)
thread2: пришёл SIGUSR1
thread1: завершаюсь
main: первая нить завершилась, выхожу
```

Вывод: сигнал с действием по умолчанию действует на процесс целиком, поэтому `kill` по PID извне не может удалить отдельную нить. Чтобы удалить одну нить, нужен обработчик + `pthread_exit` (вариант 3). Замечание: `pthread_exit` внутри обработчика не входит в список async-signal-safe функций, здесь это сделано только потому, что этого требует задание.

### Уровень 3 (B): `sigact.c` (надёжные сигналы)

- Диспозиция устанавливается через `sigaction`, в `sa_mask` добавлен `SIGINT`, значит на время работы обработчика `SIGINT` заблокирован.
- Блокировка продемонстрирована «засыпанием» в обработчике (`sleep(60)`; для проверки собирал с `-DNAP=3`).
- Вариант 2 (`-DSEND_SIGINT`, программа `sigact_int`): обработчик сам отправляет себе `SIGINT` через `kill(getpid(), SIGINT)`.

Вывод при отправке `SIGINT` извне, пока обработчик спит:

```
Sigact pid=399
Action is setted
Action is setted
Signal 10 is coming (SIGINT заблокирован на время обработчика)
Обработчик сигнала 10 завершается        <- SIGINT не прервал обработчик
(процесс завершён по SIGINT уже после выхода из обработчика, код 130)
```

Вариант `-DSEND_SIGINT`:

```
Signal 10 is coming (SIGINT заблокирован на время обработчика)
SIGINT отправлен себе, но он ждёт (заблокирован)
Обработчик сигнала 10 завершается
(процесс завершён по SIGINT после выхода из обработчика)
```

Замечание к тексту задания: в методичке написано `kill(SIGINT, getpid())`, но сигнатура `int kill(pid_t pid, int sig)`, поэтому правильно `kill(getpid(), SIGINT)`.

### Сравнение надёжных и ненадёжных сигналов

| | `signal` (ненадёжные) | `sigaction` (надёжные) |
|---|---|---|
| Диспозиция после доставки | сбрасывается в `SIG_DFL`, нужна переустановка | остаётся установленной |
| Окно гонки между доставкой и переустановкой | есть, второй сигнал убьёт процесс | нет |
| Блокировка сигналов | невозможна | маска процесса и `sa_mask` |
| Сигнал во время своего обработчика | не блокируется | блокируется автоматически |
| Получение старой диспозиции | возвращается из `signal` | через третий параметр `oact` |
| Стандарт | исторический (System V), оставлен для совместимости | POSIX.1 |

## Часть 2. Каналы и FIFO

### Теория (кратко)

- `pipe(fd)`: `fd[0]` для чтения, `fd[1]` для записи. Однонаправленный байтовый поток, FIFO-порядок, прочитанное из канала удаляется. Дескрипторы наследуются при `fork`, поэтому неименованные каналы связывают только родственные процессы.
- Каждый процесс закрывает ненужный конец. Если закрыты все концы записи, `read` на пустом канале возвращает 0 (EOF); запись в канал без читателей даёт `SIGPIPE`.
- FIFO (именованный канал) это файл типа `p` в файловой системе, создаётся `mkfifo` (в методичке `mknod` с `S_IFIFO`). Доступен неродственным процессам, переживает процессы, поэтому его нужно удалять (`unlink`). `open` блокируется, пока второй конец не будет открыт.
- Запись меньше `PIPE_BUF` атомарна, `read` может вернуть меньше запрошенного.

### Уровень 3 (A): `pipe_clientserver.c`

Два канала (`pipe1`: клиент → сервер, `pipe2`: сервер → клиент), клиент это отец, сервер это сын. Клиент читает имя файла из stdin, отправляет серверу и закрывает `pipe1` (признак конца запроса). Сервер открывает файл и шлёт содержимое, а при ошибке сообщение с `strerror(errno)`. Клиент выводит всё на stdout.

```
$ echo input.txt | ./pipe_clientserver
Привет, мир!
$ echo /no/such/file | ./pipe_clientserver
/no/such/file: can't open, No such file or directory
```

### Уровень 3 (B): структурированные сообщения (`fifomsg_*.c`, `mesg.c`, `mesg.h`)

Клиент и сервер это неродственные процессы, они общаются через два FIFO: `/tmp/fifo.1` (клиент → сервер) и `/tmp/fifo.2` (сервер → клиент). Порядок открытия согласован (сервер: FIFO1 на чтение, затем FIFO2 на запись; клиент: FIFO1 на запись, затем FIFO2 на чтение), иначе `open` блокируется навсегда. FIFO удаляет клиент.

Вместо «сырого» потока байтов по FIFO передаются сообщения:

```c
struct mymesg {
    long mesg_len;     /* длина данных */
    long mesg_type;    /* тип: MT_REQUEST, MT_DATA, MT_ERROR, MT_END */
    char mesg_data[MAXMESGDATA + 1];
};
```

Заголовок фиксированного размера (`MESGHDRSIZE`) читается первым, затем ровно `mesg_len` байт данных. Добавлены типы сообщений: запрос, порция данных, ошибка, конец ответа (`MT_END`, длина 0). Это решает проблему канала как «потока без границ сообщений»: клиент точно знает, где кончается ответ, поэтому один сеанс может обработать несколько запросов подряд. Чтение реализовано через `readn` (дочитывает до нужной длины, так как `read` из FIFO может вернуть меньше). Сервер работает циклом, пока клиент не закроет FIFO1.

```
$ printf 'input.txt\n/no/such\nmesg.h\n' | ./fifomsg_client
Client: вводите имена файлов (Ctrl+D - выход)
Привет, мир!
[ERROR] can't open: No such file or directory
/* Структурированные сообщения поверх FIFO (уровень 3 B) */
...
Server: запрос на файл 'input.txt'
Server: запрос на файл '/no/such'
Server: запрос на файл 'mesg.h'
Server: клиент закрыл FIFO, выход
```

### Сравнение pipe и FIFO

| | pipe | FIFO |
|---|---|---|
| Имя в файловой системе | нет | есть (файл типа `p`) |
| Кто может использовать | только родственные процессы | любые процессы |
| Время жизни | пока открыт хотя бы один дескриптор | пока не удалён `unlink` |
| Создание | `pipe()` | `mkfifo()` / `mknod()` |
| Направление | однонаправленный | однонаправленный (для диалога нужны два FIFO) |

## Выводы

1. Сигнал с действием по умолчанию действует на весь процесс, отдельную нить так убрать нельзя; нужен обработчик и `pthread_exit`.
2. `signal` ненадёжен, для серьёзного кода нужен `sigaction`: он сохраняет обработчик и позволяет блокировать сигналы на время обработки.
3. Неименованные каналы просты и эффективны для связи родственных процессов, но не имеют границ сообщений и работают только между родственниками.
4. FIFO снимают ограничение родства, но требуют аккуратного открытия концов и удаления файла; структурированные сообщения (заголовок + данные) решают проблему границ сообщений.
